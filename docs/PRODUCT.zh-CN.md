# 产品定义

[English](PRODUCT.md)

## 1. 产品命题

Voren 是一个面向单一可信用户、处理邮件与日程工作流的行动 Agent。它通过
受控工具执行任务，并把经过选择和验证的经验转化为带版本的程序性 Skill。

产品刻意比通用个人助理更窄。它最重要的产物，是围绕真实外部副作用建立一条
可信的学习闭环：

```text
用户请求 -> 外部行动 -> 观察结果 -> 候选学习 -> 评测 -> 晋升
```

## 2. 问题定义

LLM 经常能够完成一次性的邮件或日程任务，但一个长期存在的 Agent 会带来
更困难的问题：

- 邮件和其他工具返回是不可信数据，其中可能包含指令；
- 发送消息或修改日历会真实改变外部环境；
- 重试可能重复执行不可逆操作；
- 用户的一次纠正可能是长期偏好、可复用流程，也可能只是一次性事实；
- 从一条成功轨迹生成的 Skill 可能让其他任务退化；
- 人能读懂 Skill diff，不代表已经证明 Agent 行为变好了。

Voren 把这些问题视为运行时与评测问题，而不是提示词编写问题。

## 3. 主要用户

第一个用户是一个使用 Voren 代表自己行动的可信操作者。初始系统不是多租户
系统，也不假设需要隔离彼此不信任的人类用户。

## 4. 黄金工作流

参考场景如下：

> 找到 Alice 关于项目评审的邮件，对比邮件中的候选时间和我的日历，安排
> 本周一次 30 分钟会议。先向我展示准确的回复内容和日程事件，我确认之后
> 再发送回复并创建日程。以后和 Alice 约会时优先安排 30 分钟，并避开我的
> 午休时间。

选择这个场景，是因为它可以同时覆盖：

- 跨邮件和日历的多步工具调用；
- 时间与参与人推理；
- 外部数据与可信用户意图的分离；
- 对精确副作用的审批；
- 幂等写入和后置条件验证；
- 用户画像记忆与程序性 Skill 的分类；
- 对经过验证的经验进行后续复用。

## 5. 产品行为

### 5.1 执行任务

Voren 接收自然语言请求，组装相关用户画像和 Skill 上下文，并运行一个有界的
模型/工具循环。模型可以提出工具调用，但不能直接调用外部 Adapter。

### 5.2 控制外部副作用

每个工具都要声明副作用类型、前置条件、审批规则、幂等策略和 Verifier。
外部写操作依次经过：

```text
prepare -> authorize -> commit -> verify
准备     -> 授权       -> 提交   -> 验证
```

审批绑定到规范化后的精确动作参数。参数发生实质变化后，原审批立即失效。

### 5.3 记录证据

每个 Run 都会产生一条追加写事件流，覆盖模型轮次、选中的 Skill、动作提议、
策略判断、审批、工具观察、状态验证、失败以及最终结果。

### 5.4 保守学习

一次已完成的 Run 不会自动变成 Skill。学习路由器首先从以下类型中选择：

- 不进行长期写入；
- 生成用户画像或偏好候选；
- 保留为 Episode；
- 生成程序性 Skill 候选。

候选对象保留原始证据引用，在相应评测门槛通过之前始终处于非激活状态。

## 6. 信任模型

初始信任分类如下：

| 来源 | 默认信任级别 | 能否授权动作 | 能否直接更新长期学习对象 |
| --- | --- | --- | --- |
| 系统策略 | 可信 | 可以 | 仅限策略 |
| 操作者直接请求 | 可信意图 | 可以，但仅限已表达范围 | 仅限明确表达的偏好 |
| 操作者明确纠正 | 可信证据 | 可以 | 可成为候选证据 |
| 模型输出 | 不可信提议 | 不可以 | 不可以 |
| 邮件、文档或工具结果 | 不可信数据 | 不可以 | 不可以 |
| 确定性 Verifier | 可信证据 | 不可以 | 可成为候选证据 |

不可信数据可以影响任务参数，例如邮件里发现的会议日期，但它不能扩大权限，
也不能自动成为长期指令。

## 7. 初始需求

### 功能需求

- 运行支持取消和确定性停止原因的有界工具调用循环；
- 通过 Adapter 使用 AgentDojo 的邮件和日历工具；
- 为精确副作用审批暂停和恢复 Run；
- 在重试和结果不明确的超时场景中避免重复外部修改；
- 每次外部修改后验证后置条件；
- 持久化一条可重建且带来源信息的 Run Trace；
- 通过渐进披露加载带版本的 Skill；
- 从选定证据中创建非激活 Skill 候选；
- 在同一组 held-out 用例上比较 active 与 candidate 版本；
- 晋升和回滚到某个精确、不可变的 Skill 版本。

### 质量需求

- 策略和验证必须由确定性代码强制执行，不能只写在提示词中；
- Secret 和敏感工具参数必须从普通日志中脱敏；
- 必须记录模型、提示词、工具 Schema、Skill、数据集和 Evaluator 版本，以便
  复现实验；
- 核心领域逻辑必须可以在没有在线模型和网络的情况下测试。

## 8. 第一个版本的非目标

- 多 Agent 规划、委派或审查；
- Mission DAG、分布式 Lease 或 Worktree 编排；
- 长期运行的全渠道 Gateway；
- 自动 Cron 或 Heartbeat 行为；
- 通用插件市场；
- 浏览器或桌面 GUI 自动化；
- 通用向量记忆平台；
- 同时支持多个真实邮件/日历供应商；
- 仅根据 LLM 判断或一次成功执行就自动在线晋升。

## 9. 产品级完成条件

第一个可以用于作品集的版本应证明：

1. 黄金工作流能够在受控环境中端到端完成；
2. 没有配置所要求的授权时，不会执行外部修改；
3. 邮件中的注入指令不能授权无关动作；
4. 重试和恢复不会重复发送邮件或创建日程；
5. 系统检查最终外部状态，而不是看到工具成功返回就默认成功；
6. 不良 Skill 候选会被可重复的 Gate 拒绝；
7. 晋升后的 Skill 可以追溯到原始证据，并支持回滚；
8. 评测报告基于固定 Baseline，不虚构任何结果。
