# 模拟面试、项目表达与经历核对

编写日期：2026-09-22。面向 AI 应用 / Agent 开发社招。本文用于练习；它不能把“仓库已有功能”转换成“本人独立设计并熟练掌握”。

## 1. 三件事分别准备

| 环节 | 对方在判断什么 | 你需要准备什么 |
|---|---|---|
| 简历筛选 | 岗位关键词、开发经历、项目相关性 | 已定稿简历、真实技能范围、对应项目亮点 |
| 获得沟通机会 | 当前岗位与个人情况是否匹配 | 简短介绍、可讨论的技术方向、客观时间信息 |
| 技术面试 | 能否解释、修改、排错和做取舍 | 代码调用链、状态变化、故障实验和条件化设计 |

前两项完成不代表第三项自动完成。以后主要围绕技术面试练习，无需反复重写简历。

## 2. 60—90 秒自我介绍的结构

按事实分三段，每段只承担一个目的：

1. **背景**：2025 年湖北文理学院自动化专业毕业；2025-06-30 至 2026-09-11 在 360 从事软件开发，工作涉及 Java 后端和 C++/Linux 客户端。
2. **方向**：现在关注 AI 应用 / Agent 开发，个人项目分别研究单 Agent 外部操作与 Skill 迭代、多 Agent 软件开发协作。
3. **本次重点**：选择最能展开的一个问题，例如外部操作超时恢复或测试证据绑定，邀请面试官往这个方向追问。

**可使用的事实版示例：**

> 我是 2025 年毕业，之前在 360 做了一年多软件开发，工作涉及 Java 后端和 C++/Linux 客户端，包括软件管理、文件上传和终端相关模块。现在求职方向是 AI 应用与 Agent 开发，个人项目主要有 Voren 和 RunGuild：前者围绕邮件日程任务，处理工具执行、人工确认、结果校验和 Skill 版本迭代；后者围绕多 Agent 开发协作，把需求规划、任务调度、代码执行、测试和评审串起来。项目用了较多 AI 辅助编码，我会结合实际读过和验证过的代码说明自己的参与范围。

这段可以随掌握程度补充一个本人完成的具体实验，但不要补“独立架构”“生产落地”“效率提升”等未经支持的描述。实际面试可以自然缩短，不需要逐字朗读。

## 3. Voren：不同长度的项目介绍

### 30 秒：先让对方知道项目在解决什么

> Voren 是邮件与日程任务的单 Agent 应用。它让模型查询信息和提出操作方案，外部变更先经过人工确认，程序执行后再核对实际结果。另外，它把有来源的执行记录和人工纠正用于受控 Skill 候选迭代，经过评测再决定是否启用。

### 2 分钟：讲一个请求，而不是背组件表

> 以根据邮件安排日程为例，程序先组装用户请求、当前 Skill 和偏好上下文，把工具定义交给模型。模型返回查询工具调用后，程序执行查询，再把结果追加到消息列表，形成多轮调用。遇到创建日程这样的外部操作时，程序生成包含预期效果的提案并保存，Run 进入等待审批。用户批准原提案后，由动作网关执行并查询外部状态，生成回执。结果不明确时进入对账流程，不直接重发。Skill 更新是另一条路径：先提交有证据的候选，在指定用例上比较基线与候选，再显式启用或回滚。程序只检查显式登记的案例重叠，评测数据的真正独立性需要另外保证。

> 当前范围是受控个人项目。Google 连接器有实现，但没有真实账号验证证据；运行时检查点、Web 审批恢复与真实模型跨进程恢复也有不同边界，不能合并宣传成完整断点续跑。

**面试官追问入口：** 审批绑定哪些字段？operation ID 与 Run ID 是否相同？已成功但本地超时怎么办？评测通过为何不立即启用？当前真正未完成的恢复是什么？

### 5 分钟：增加一条故障时间线

在上述介绍后，只选一条展开：外部变更发生 → 保存回执前崩溃 → 重启读取原操作 → 查询外部状态 → 匹配预期效果 → 补写回执。解释为什么每一步需要稳定身份，以及没有可靠外部查询能力时仍然可能无法恢复。用 [Voren 问答](02-VOREN-INTERVIEW-QA.md) 中对应题目练习追问。

## 4. RunGuild：不同长度的项目介绍

### 30 秒

> RunGuild 是多 Agent 软件开发协作项目。它把需求讨论转换成带依赖关系的任务计划，按角色调度 Agent 执行；代码在 Task Worktree 中处理，按计划收集证据，需要评审时提交固定版本和材料，集成时再验证候选结果。平台还支持用户与 Agent 共同编辑项目文档。

### 2 分钟

> 用户从对话发起需求，Planner 输出任务与依赖，人工批准后开始调度。PostgreSQL 保存任务、执行尝试和租约等事实状态，Redis 主要承担通知。Worker 认领任务后加载冻结的任务和 Skill 上下文，再按当前运行配置调用模型与工具。代码任务使用 Worktree 分离工作目录，完成时按计划检查必需证据，需评审任务另查独立评审；集成 Worker 在临时候选中验证合并结果。Worker 中断依靠租约到期回收，续租和工具结果提交各自校验令牌，任务完成另依赖状态、证据与集成门禁。

> 当前已实现需评审代码任务的主要流程，也保留了实际运行记录，但没有足够实验支持多 Agent 比单 Agent 更快或更省钱。仍需补强 Worker 有效配置冻结、无评审任务的集成分支，以及发布时对当前 HEAD 与批准快照的再次核对。测试断言是否充分覆盖需求要另行验证；Worktree 也不提供操作系统级隔离。

**面试官追问入口：** 为什么用数据库调度？Outbox 解决什么？旧 Worker 还能写文件怎么办？评审与代码变更如何绑定？为什么合并后再测？Yjs 能保证哪些性质、不能保证哪些业务语义？

### 5 分钟

增加“测试 A 提交通过、随后代码变成 B 提交”的反例，解释 attempt、commit、tree、当前评审提交和较新失败记录分别起什么作用。最后给出独立验收环境的改进方案，明确它是下一步设计。对应材料见 [RunGuild 问答](04-RUNGUILD-INTERVIEW-QA.md)。

## 5. 常见经历追问：可以怎么答

### B01. 工作内容与 AI 无关，为什么投 Agent 开发？

> 工作中积累的是后端与客户端开发基础，个人项目用来学习模型与工具协作后的新问题。例如重复请求、失败恢复、状态一致性是能够迁移的工程问题；模型会生成不确定的调用、上下文会增长、工具结果可能不可信，则是需要另外学习和验证的部分。

后续举一个真实工作场景和一个真实项目机制，不把两者混成同一段工作经历。

### B02. 代码是不是 AI 写的？

> 这两个项目大量使用了 AI 辅助编码。我的实际参与范围是【本人完成的工作】。我可以结合【已读懂的调用链】和【本人执行的实验】解释设计，也能说明当前有哪些不足。

这三个位置必须用真实内容填。刚开始学习时就说正在接管和理解；完成练习后再说自己已验证、修改了哪些部分。不要以“AI 只是补全”掩饰事实，也不要把“运行过一次”说成独立设计。

### B03. 你本人最熟悉哪一部分？

选择最近完成实操的模块，回答输入、核心处理、状态保存、异常路径和一次实验。例如“审批重放”比“整体架构我都很熟”更容易验证。面试官继续追问时，打开对应逻辑在脑中走一遍，而不是换成术语清单。

### B04. 你遇到最大的难点是什么？

难点应是本人真正调查过的问题。可以使用以下结构：现象 → 原判断 → 找到的证据 → 排除的解释 → 修改/验证 → 剩余边界。仓库历史修复可以作为学习案例，但未亲自参与时不能说“当时我排查出来”。

### B05. 项目效果如何，有多少用户？

> 当前是个人项目，已有代码、测试与部分运行记录，没有可报告的生产用户规模。效果会按任务结果、失败类型和运行开销评估，现有小样本不能支持普遍效率提升。

如果被要求给数字，使用能够定位到原始记录并说明实验条件的数据；不会就说需要核对，不临场创造。

### B06. 为什么不直接用成熟框架？

> 这个项目的重点是把执行边界和状态机制明确写出来，便于检查审批、恢复和证据如何衔接。手写的代价是要自己维护协议适配、checkpoint 和调度。若进入实际团队，会按现有技术栈、可观测性、恢复语义和维护成本评估框架，而不是坚持全部自研。

这里解释的是项目取舍，不意味着所有实现都由本人最初决策。

### B07. 如果重做一次，优先改什么？

Voren 可以选择“真实模型与 Web 恢复衔接”“请求 reservation 后的崩溃恢复”；RunGuild 可以选择“独立验收标准”“入口可恢复提交”“不可信代码隔离”。说出触发场景、现有风险、最小改造和验证方法，避免只说“上容器、加队列、做监控”。

### B08. 为什么学了这本书，还不能直接说掌握 Agent？

书帮助建立概念框架；项目验证需要处理具体接口、状态和故障。可以用读书解释设计选择，用代码和实验说明理解到什么程度。书名不是效果证明，不需要在每个回答里重复。

### B09. 为什么离职、为什么选择城市、薪资期望？

这些信息目前没有足够事实，必须本人补充。只整理自己的真实原因、约束和期待，不套用“业务调整”“组织裁撤”等未经确认的故事。技术文档不代替个人情况说明。

### B10. 你有什么问题问我们？

可选两三个真正影响工作的主题：Agent 主要服务什么业务；外部操作如何审批与审计；上线效果用什么标准验收；团队更需要业务应用、平台工程还是模型训练；入职后前三个月预期交付什么。根据面试中已经得到的信息调整，不重复提问。

## 6. 如何保存自己的技术故事

每次完成一个实验，填一张卡，不预先写成“成功案例”：

| 项目 | 记录内容 |
|---|---|
| 触发问题 | 具体输入和症状，不写泛泛的“稳定性不好” |
| 环境 | Git commit、模型或 Fake、依赖、数据库、命令 |
| 初始判断 | 当时认为哪里出问题，为什么 |
| 关键证据 | 日志、SQL 行、消息列表、提交哈希、测试输出 |
| 动作 | 自己查了什么、改了什么、为什么 |
| 结果 | 实际观察，不写未测的性能收益 |
| 局限 | 没覆盖的窗口、外部依赖和后续问题 |
| 可追问点 | 至少三个可能追问及代码位置 |

例如“发现真实模型适配器依赖内存缓存”是一条代码审查发现；只有执行重建实验并记录结果后，才能再增加“本人复现”这一层证据。

## 7. 三套模拟面试流程

### 第一次：30 分钟，只检查是否真正读过 Voren

| 时间 | 内容 | 面试官要观察什么 |
|---|---|---|
| 0—3 分钟 | 简短介绍与个人参与范围 | 是否清楚区分工作、项目和 AI 辅助 |
| 3—10 分钟 | 画一次请求的消息流与审批状态 | 是否知道模型输出与实际执行的边界 |
| 10—20 分钟 | 外部成功但本地超时；进程重启 | 是否能定位数据与恢复动作 |
| 20—26 分钟 | Skill 为什么要评测再启用 | 是否理解证据、独立用例和版本绑定 |
| 26—30 分钟 | 复盘 | 记录两个最需要补的点 |

### 第二次：45 分钟，RunGuild 深挖

先用 5 分钟讲全链，再分别用约 10 分钟讨论任务认领与过期 Worker、代码证据与集成、上下文/协作文档，最后复盘。围绕一条具体失败追问到底，不在几十个名词之间跳转。

### 第三次：60 分钟，接近综合技术面

| 时间 | 内容 |
|---|---|
| 0—5 分钟 | 自我介绍及工作中真实模块 |
| 5—20 分钟 | 一个主项目深挖 |
| 20—30 分钟 | 工具调用、RAG、上下文与评测机制 |
| 30—45 分钟 | 从场景文档任选一题，画方案并推演故障 |
| 45—55 分钟 | 小编码或 SQL/状态机题 |
| 55—60 分钟 | 候选人提问与复盘 |

实际练习时一次只问一道题，等回答后再根据内容追问。题库是储备，不是一次面试必须覆盖的清单。

## 8. 回答评分与补习分流

| 等级 | 观察到的回答 | 下一步 |
|---|---|---|
| 未形成解释 | 重复题目或罗列术语 | 回到架构文档，画具体数据流 |
| 概念正确 | 能说定义，不能定位实际项目 | 找入口、核心函数、测试 |
| 机制清楚 | 能解释状态和失败路径 | 做故障实验或小修改 |
| 能验证与取舍 | 解释证据、替代方案与限制 | 换一个条件不同的新场景 |

以下问题优先纠正：把读工具结果当成可信指令；把数据落盘等同于远端恰好一次；把临时目录当安全沙箱；把模型回答完成等同于业务验收；把单测数量等同于生产能力；用未经完成的学习目标描述当前技能。

## 9. 面试前的事实核对表

- [ ] 工作日期、公司名称、职位和实际业务一致。
- [ ] 工作中的 Java/C++ 经历没有被改写成 AI 项目。
- [ ] 每条个人参与描述都有本人行为支持。
- [ ] 能解释简历上出现的 Python、RAG、MCP、Skill、上下文和多 Agent 等内容。
- [ ] 清楚 Voren 的 Google 范围、Web 恢复与 provider 恢复限制。
- [ ] 清楚 RunGuild 的独立验收、入口恢复、宿主执行与成本报告限制。
- [ ] 所有数字都有来源和实验条件；不存在用假设练习数据充当项目指标。
- [ ] 至少准备一个本人完成的调试/修改案例，一个承认局限并提出验证方案的案例。

若某项尚未完成，就把它作为接下来的练习目标，不用通过更强的措辞掩盖。
